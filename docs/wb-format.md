# `.wb`（旧 WhiteBrowser）フォーマット解析仕様書

- 対象トラック: GrayBrowser Phase 4 先行サブタスク（`.wb` 解析・匿名化）
- 解析元: 実データ 1 件（`default_20110504.wb`、movie 3072 件規模）
- ステータス: **フォーマット構造 確定**（実データ保有者による答え合わせ済み）
- 注意: 本書には実データ由来の個人情報（実パス・実タグ・実ファイル名）は転記していない。統計・型・オフセットのみ記載。

---

## 1. 結論（最重要）

**`.wb` は独自バイナリではなく、標準の SQLite3 データベースファイルである。**

- マジックバイト: `53 51 4c 69 74 65 20 66 6f 72 6d 61 74 20 33 00`（`SQLite format 3\0`）
- ページサイズ: 1024 バイト
- **エンコーディング: UTF-8**（ヘッダ 0x38 のテキストエンコーディング値 = 1）。当初懸念していた Shift_JIS ではない。日本語のパス・タグはそのまま UTF-8 で読める。
- 結果として **リバースエンジニアリング不要**。標準の SQLite ドライバ（Rust なら `rusqlite`）でそのまま開ける。

### 設計方針との整合（`gb-core` 純粋クレート制約）

basicdesign v8 で `gb-core` は `rusqlite` に依存しない純粋クレートと定義されている。したがってパーサは「バイト列 → 構造化データ」ではなく、次の形で実装する:

- SQLite への接続・SELECT 実行は **アダプタ trait**（`src-tauri` 側 or テスト側で実装）に切り出す
- `gb-core` 側は「アダプタが返した行データ（`Vec<WbMovieRow>` 等の素の値）→ GrayBrowser のドメインモデルへの純粋変換」を担い、これを unit test で網羅する
- スコア変換・タグ分割・サムネイル hash 抽出などの**変換ロジックはすべて純粋関数**にできる（後述）

## 2. テーブル構成（実データ: movie 3072 件）

| テーブル   | 件数 | 役割                                        | Phase 4 での扱い                 |
| ---------- | ---- | ------------------------------------------- | -------------------------------- |
| `movie`    | 3072 | 動画 1 件 = 1 行。パス/タグ/評価/ハッシュ等 | **移行の主対象（要件-13/14）**   |
| `tagbar`   | 17   | サイドバーのタグ/検索ツリー定義             | 移行不要（参考情報）             |
| `watch`    | 45   | 監視フォルダ設定                            | 移行不要（要件-01 で再設定）     |
| `profile`  | 25   | スキン別の UI 設定（`skin`,`key`,`value`）・**検索履歴・タグ候補** | `thum_size` のみ参照。他は移行対象外だが**個人情報を含む** |
| `system`   | 42   | バージョン・スキン名等の全体設定            | 移行不要                         |
| `sysbin`   | 6    | ツールバー配置のバイナリ blob               | 移行不要                         |
| `findfact` | 150  | 検索語の頻度                                | 移行対象外・**個人情報**         |
| `history`  | 30   | 検索履歴                                    | 移行対象外・**個人情報**         |

`watch` テーブルの内容は移行しない。代わりに、インポート時に今回登録した動画（オンライン・オフラインとも）の親フォルダを監視フォルダへ自動で追加する（不要なフォルダは後から監視フォルダの設定で外せる）。オフライン動画（旧外付けHDD・停止中のNAS等のパス）の親フォルダも対象とし、到達できない間もサイドバーにフォルダとして表示される（オフラインの表示は、そのフォルダ配下の動画の行に出る）。登録済みでスキップした動画の親フォルダは対象外（再インポートで二重に追加しない）。親フォルダ区間に `?` が残ったパス（復元できなかった行）は、実在しない監視フォルダになるため対象外。ドライブ直下（`D:\`）と共有ルート（`\\server\share\`）は、1本の迷い込んだファイルでドライブ全体を監視しないよう追加しない。既存の監視フォルダと包含関係（同一・配下・親）にあるフォルダも、二重監視を避けるため追加しない。残った追加先のフォルダ同士が包含関係にある場合は外側の1つにまとめる。

### 3.3 スコア変換の申し送り

`score>5` の 89 件を 5 にクランプする。Phase 4 の移行ログに「丸めた件数（=89）」を出力し、ユーザーに提示する設計とする。按分（上位 X% を星 5 等）は保有者意向により**採用しない**。

### 3.4 ★だけのタグの扱い

WhiteBrowser では `★` / `★★★` のような★だけのタグを評価として使う運用があった。インポーターは次の規則で評価に変換する。

- **判定**: 全角→半角折りたたみと trim の後、空でなく全文字が `★`（U+2605）のタグを「★タグ」とする。`☆`、`★お気に入り`、`★ ★`、`★☆` など他の文字を含むものは通常タグのまま。
- **変換**: ★の数が評価（上限 5。6 個以上は 5）。変換した★タグは通常タグとして登録しない。
- **優先順位**: ★タグと `score` が両方ある動画は★タグを優先する。★タグが複数ある動画は最大値を採用する。★タグが無ければ従来どおり `score` から変換する。
- **`source_tag_count`**: ★タグを除いた数。★タグは `video_tags` に書かれないため、含めると `tags_assigned` が不足して見え、結果画面が「要確認」を誤表示する。
- **結果画面**: 新規登録された動画のうち★タグから評価にした件数（`ratings_from_star_tags`）は集計するが、結果画面には表示しない。登録済みでスキップされた行は数えない。
- 取り込み済みデータの修復は行わない。

### 3.5 パスの `?`（変換できなかった文字）の復元

`movie_path` / `movie_name` には、ディスク上の文字が `?`（U+003F）に置き換わって保存されている行がある。旧 WhiteBrowser が文字コード変換の際、変換先に無い文字を `?` にしたものと見られる（旧 WhiteBrowser 側の挙動は未確認）。Windows のファイル名には `?` を使えないため、`?` は「ここに元の1文字があった」という確かな目印になる。

- **確認できている範囲**: 長いダッシュ（U+2014）のみ。実データ 126 行中 3 行で、親フォルダ内に `?` を任意の1文字とみなして一致する名前がちょうど1つあり、その位置の文字は U+2014 だった。
- **未確認**: 全角チルダ（U+FF5E）など U+2014 以外の文字が `?` になるか。`?` になる文字の全集合。
- **復元規則**: 保存されたパスがそのままでは存在せず、`?` を含むときだけ試す。ルート（`D:\`、`\\server\share\`）以降を先頭から順に解決し、`?` を含む区間は、解決済みの親フォルダの直下を列挙して `?` を「ちょうど1文字」として照合する（`?` 以外の文字は大文字小文字を区別しない）。**一致がちょうど1件のときだけ**採用する。0 件・複数件・列挙できない（NAS 停止等）ときは復元せず、従来どおりオフラインとして取り込む。`\\?\` 接頭辞のパスは対象外。
- **復元した場合**: 復元後のパスを `file_path` に使い、`file_name` も復元後パスの最終区間にする（`movie_name` の `?` は残さない）。以降は通常の動画として扱う。
- 取り込み済みの `?` のままの行は修復しない。再インポートすると、復元後のパスの別の行として追加される。

### 3.6 機種依存文字を含むファイル名

通常のスキャンと同じ検査（`gb_core::filename_validation::is_machine_dependent_filename`）を、各行のファイル名（3.5 の復元後の名前）に対して、ハッシュ計算より前に行う。該当した行は `videos` に登録せず、ハッシュ計算・サムネイル生成も行わず、`skipped_files` に記録して「未登録」パネルに出す（結果画面には `skipped_invalid_name` として件数を出す）。

- オフライン行も、名前だけで判定するので同じ扱い。
- 該当行の親フォルダは監視フォルダの自動追加の対象外。
- 該当行の旧サムネイル JPG（`.#<hash>.jpg`）は、4.2 の `thumbnails_unmatched` にも `thumbnails_skipped_online` にも数えない（登録しない動画の JPG を手動対応に回さないため）。
- 登録済みのパスの行でも、検査は無条件に行う（通常のスキャンと同じ）。取り込み済みデータの修復は行わない。

## 4. 要件-14: サムネイル紐付け（オフライン動画の旧 JPG 移行・確定）

### 4.1 旧サムネイルのファイル命名規則（保有者確認済み）

```
[動画のファイル名].#<hash>.jpg
例) MyVideo.mp4.#1e5e0fbf.jpg
```

- `#` 直後の **8 桁 hex = `movie.hash`**。実データで hash は全件小文字 8 桁 hex かつ一意（3071 件）であることを確認済み。
- したがって紐付けは **hash 一本で解ける**。ファイル名部分（`[動画のファイル名]`）は照合に使わなくてよい。

### 4.2 紐付けアルゴリズム（オンライン/オフラインで分岐）

要件-14 の原文は「（実ファイルが手元にない）**オフライン動画であっても**サムネイル付きでカタログ移行できる」ことをゴールとしている。したがって旧 JPG サムネイルの移行は**オフライン動画に限定**する。実ファイルが手元にあるオンライン動画は、旧 JPG を移行せず、動画本体から新規にサムネイルを生成する（そのほうが高品質で、既存のサムネイル生成パイプラインをそのまま活用できるため）。

インポート時、各動画レコードについて:

1. **オンライン動画（実ファイルが存在）:** 旧 JPG を移行しない。既存のサムネイル生成パイプライン（未生成分を拾う `enqueue_missing_thumbnails` 相当）に載せ、動画本体から WebP を新規生成する。
2. **オフライン動画（実ファイルが未接続）:** 旧サムネイルフォルダから該当 JPG を探して移行する。
   - 旧サムネイルフォルダ内の各ファイル名から `\.#([0-9a-f]{8})\.jpg$` で hash を抽出
   - `movie.hash` と突合し、対応する動画レコードを特定
   - basicdesign 3.3 / 5 章に従い、JPG → WebP 変換、UUID にリネームして `GrayBrowser\thumbnails\` へ配置（アトミック書き込み）
   - これにより、動画本体が未接続でもサムネイル付きでカタログ移行できる（要件-04/14 のゴール）

> **サマリーの集計定義:** 旧サムネイルフォルダ内のファイルは次の3区分で数える（ファイル単位）。
> - `thumbnails_skipped_online`: hash がオンライン動画の `movie.hash` に一致するファイル。移行対象外（動画本体から新規生成）であり、エラーでも要対応でもない。ログには残すが、結果画面には表示しない（取り込めなかったと誤解されるため）。
> - `thumbnails_unmatched`（未対応）: 上記にも、オフライン動画にも一致しないファイル（命名規則に合わない、JPG 以外の `Thumbs.db` 等、どの `.wb` 行にも存在しない hash）。ユーザーの手動対応が必要な候補。
> - 同一 hash がオフライン動画にも一致する場合はオフライン側の移行を優先する。
> - 同じ `.wb` を再インポートして登録済み（スキップ）になったオンライン動画の旧 JPG も `thumbnails_skipped_online` に数え、`thumbnails_unmatched` には含めない（登録済みのオフライン動画の旧 JPG は再移行しない）。

> **補足（Phase 4 実装で確定）:** 旧サムネイルフォルダが指定されない場合や、オフライン動画に対応する JPG が見つからない場合は、そのサムネイルは未設定のままとし、移行自体は成功として扱う（`thumbnails_linked` / `unmatched` を移行サマリーに計上）。オンライン動画のサムネイルは旧フォルダの有無にかかわらず動画本体から生成される。

### 4.3 旧サムネイルの6コマ切り分け（`profile`）

旧サムネイルの JPG は、複数のコマが横に連結された**1枚の画像**である。コマの並びは `profile` 表（列 `skin`, `key`, `value`）の `key = 'thum_size'` に `<幅>x<高さ>x<列数>x<行数>` で記録されている（実データ: `200x150x6x1`、同表の `img_width=1200` / `img_height=150` はその結果の画像サイズで、移行では使わない）。`thum_size` はスキンごとの設定で、実データでは `Search_table` の1行のみ。

インポーターは、オフライン動画の旧 JPG を次の規則で取り込む。

- **切り分けるのは次の条件をすべて満たすときだけ。** (1) `thum_size` が全スキンで同じ1種類の値で、4要素すべてが正の整数として読める。(2) 列数×行数がちょうど6（GrayBrowser のサムネイルのスロット数）。(3) JPG の実寸が（幅×列数）×（高さ×行数）に一致する。
- 切り分けるときは、左上から行優先でコマを切り出し、i 番目のコマをスロット i（`[id]_i.webp`）に WebP で書く。通常のスキャンで作る6枚のサムネイルと同じ見え方になる。
- 上記を満たさない場合（`thum_size` が無い・読めない・スキン間で値が違う、6コマでない、実寸が合わない、実寸を取得できない）は、従来どおり画像全体を WebP に変換して6スロットすべてに入れる。
- 切り分けの途中で失敗した動画は、全スロットを削除して失敗として数える（画像全体への切り替えはしない）。

> **確認できている範囲:** 実データで確認できているのは `200x150x6x1`（6コマ×1行）のみ。他のスキン・並びは従来経路で扱う。

`profile` には文字化けするバイナリ値の行もあるため、必要なキーの `value` だけを文字列として読み、文字列でない行は読み飛ばす。

## 5. 匿名化ツールへの申し送り（最重要・個人情報保護）

### 5.1 原則

個人情報は `movie` テーブルだけに留まらない。**設定・履歴系テーブルにも実ファイル名・実タグが残る**ことを実データで確認した（例: `profile.lastfind` に最後の検索語、`profile` のタグ候補キー、`findfact`/`history` に検索履歴）。

→ 匿名化の網羅性テストは「movie だけ検査」では**不十分**。全テーブルの text 列を対象にする。

### 5.2 匿名化対象 text 列の全リスト（実データから機械抽出）

| テーブル   | 個人情報を含みうる text 列                                                                                                                                                                                                                                                     |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `movie`    | `movie_name`, `movie_path`, `hash`, `title`, `artist`, `album`, `grouping`, `writer`, `genre`, `track`, `camera`, `create_time`, `kana`, `roma`, `tag`, `comment1`, `comment2`, `comment3`（`container`/`video`/`audio`/`extra` はメタ情報だが text 列として走査対象に含める） |
| `findfact` | `find_text`                                                                                                                                                                                                                                                                    |
| `history`  | `find_text`                                                                                                                                                                                                                                                                    |
| `profile`  | `key`, `value`（`lastfind`・タグ候補・`dir0` 等に実データ）                                                                                                                                                                                                                    |
| `tagbar`   | `title`, `contents`（ユーザー定義タグ名が入りうる）                                                                                                                                                                                                                            |
| `watch`    | `dir`（監視フォルダの実パス）                                                                                                                                                                                                                                                  |
| `system`   | `value`（`skin` 名等。実害は低いが走査対象）                                                                                                                                                                                                                                   |

> `hash` は個人情報そのものではないが、サムネイル命名と結合すると実ファイル名の痕跡になりうるため、匿名化時は**決定的な別 hash に一貫置換**し、サムネイルフィクスチャ側の命名とも整合させる。

### 5.3 匿名化の要件

- **決定性**: 同一入力 → 同一ダミー出力（同じ実パスは常に同じダミーパスへ）。テスト再現性のため。
- **参照整合**: `movie.hash` を置換したら、サムネイルフィクスチャのファイル名 `.#<hash>.jpg` も同じ規則で置換し対応を保つ。
- **網羅性テスト（必須）**: 匿名化後のフィクスチャに実データ由来文字列が 1 つも残っていないことを検証する自動テスト。全テーブル全 text 列を走査し、既知の実データトークン（実ドライブ文字の並び・実タグ等）が出現しないことを assert。
- **構造保存**: 件数・改行区切りタグ・score 分布などの構造的性質は保ったままにする（パーサ/インポーターのテストに使えるように）。

| 項目                                       | 確信度 | 備考                                                                                                                          |
