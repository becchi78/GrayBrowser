# リリースの仕組み

GrayBrowser のリリースは、利用者の PC に入るコードを更新する経路を守ることを目的に設計している。このアプリは、インストーラーを配布するだけでなく、アプリ内から更新を適用する(自動更新)。更新の経路が乗っ取られると、利用者の PC で任意のコードが実行されるため、「誰が、どの条件で、署名付きの更新を作れるか」を絞っている。

このドキュメントは、メンテナーと、リリースまわりの変更に関わるコントリビューター向け。実際のリリース手順の細かい操作(コマンドなど)ではなく、**仕組みと、その設計の理由**をまとめる。

## 全体の流れ

```
コードのゲート      PR のレビュー承認 → main にマージ
                         │  (ここではリリースは始まらない)
リリースの引き金    管理者が v* タグを作って push
                         │  タグの push で GitHub Actions が起動
鍵のゲート          Environment「release」の承認(Review deployments)
                         │  承認されて初めて署名鍵が渡され、ビルドが始まる
ビルドと署名        windows-latest でインストーラーをビルドし、署名
                         │  latest.json(更新マニフェスト)を生成
Draft の作成        Draft の Release を作成(誰にも配信されない)
                         │
公開のゲート        人が Release の内容を確認して「公開」
                         ↓  公開した瞬間に、アプリ内更新の配信が始まる
```

ゲートを分けているのは、「コードを入れてよい」と「いま署名して配信してよい」を別の判断にするため。マージしただけでは配信されない。

## 各部の役割

### 1. 署名とアプリ内更新

- インストーラーは、**署名鍵(秘密鍵)**で署名される。アプリには**公開鍵**が埋め込まれていて(`src-tauri/tauri.conf.json` の `plugins.updater.pubkey`)、公開鍵で検証できない更新は適用されない。
- 更新の情報は、最新の公開済み Release に添付された `latest.json`(バージョン、リリースノート、署名、インストーラーの URL)から読む。配信元は GitHub Releases に固定されている。
- 更新は、利用者が「今すぐ更新」を押したときだけ適用される。ダウンロード後、署名を検証してから、インストーラーを起動する。
- このため、GitHub 上のファイルを差し替えられても、秘密鍵がなければ有効な署名は作れず、適用されない。

アプリ側でも、配信元の固定を守っている。
- 更新の確認は、プラグインの標準の `check()` ではなく、自前のコマンド(`check_for_update`)で行う。フロントエンドから配信元やヘッダーを自由に指定できないようにするため。
- 検証用に配信元と公開鍵を上書きする環境変数(`GB_UPDATE_ENDPOINT`、`GB_UPDATE_PUBKEY`)は、デバッグビルドにしか存在しない。リリースのビルドでは、その名前が実行ファイルに残っていないことを CI で確認している。

### 2. タグによる起動とバージョンの整合チェック

- リリースは `v*` タグの push でだけ始まる。ブランチへの push や PR では始まらない。
- タグは特定のコミットを指す不変の名前で、「どのコードをリリースするか」の根拠になる。ワークフローは、タグが指すコミットを checkout してビルドする。
- 最初のステップで、タグ名、3つのバージョン(`package.json`、`tauri.conf.json`、`Cargo.toml`)、`CHANGELOG.md` の項が一致していることを確認する。一致しなければ、ビルド前(約10分かかる)に失敗する。

### 3. 署名鍵の隔離(Environment `release`)

署名鍵は、リポジトリ直下の Secret ではなく、**Environment `release` の Secret** に保存する。Environment には次の保護ルールがある。

- **デプロイできる ref の制限**: `v*` のタグだけ。ブランチ上のワークフローからは、鍵に届かない。
- **必須レビュアー**: 承認者が Actions の実行画面で承認するまで、ジョブは `waiting` で止まる。承認されて初めて、鍵がジョブに渡される。却下すれば失敗する。

リポジトリ直下の Secret に置くと、書き込み権限者がブランチでワークフローを書き換え、鍵を外部に送るステップを足すだけで、レビューなしに鍵に届く。Environment に置くことで、この経路を塞いでいる。

鍵は、ビルドのステップにだけ環境変数として渡す。他のステップやジョブには渡さない。ワークフローの既定の権限は読み取りのみで、書き込み権限(Release の作成)は、Draft を作るジョブにだけ付けている。

### 4. タグの Ruleset

`v*` タグについて、**作成・更新・削除**を、Repository admin だけに制限している。

- 書き込み権限だけの共同開発者は、リリースのタグを作れない(= 署名鍵のゲートに到達できない)。
- 配布済みの版の根拠になるタグを、後から動かしたり消したりできない。

### 5. コードのゲート(CODEOWNERS と main の保護)

`main` への変更は PR とレビュー承認が必要。加えて、署名と配信の信頼境界になる次のファイルは、**コードオーナー(`.github/CODEOWNERS`)のレビューが必須**。

- `.github/`(ワークフロー、CODEOWNERS 自体)
- `scripts/release/`(更新マニフェスト、バージョン検査の生成コード)
- `src-tauri/tauri.conf.json`(公開鍵、配信先、バージョン)
- `src-tauri/tauri.release.conf.json`
- `src-tauri/capabilities/`(フロントエンドに許可する API)
- `src-tauri/src/commands/update_cmds.rs`(更新の確認処理)

これらを書き換えると、公開鍵の差し替え、配信先の変更、鍵の持ち出しなどに直結するため。

### 6. Draft と、人による公開

ワークフローは、Release を **Draft** までしか作らない。Draft は誰にも配信されない。メンテナーが、次を確認してから公開する。

- リリースノートの体裁(変更点、SmartScreen の案内、インストーラーの SHA256)
- 添付ファイル(インストーラーと `latest.json`)。`latest.json` のバージョンがタグと一致し、署名が空でなく、URL がこの Release のインストーラーを指していること
- 可能なら、Draft のインストーラーを実機で起動して確認する

公開すると配信が始まり、取り消しは難しい。公開前の確認を省略しない。

### 7. 生成物の検査

署名や `latest.json` が作れない、CHANGELOG に該当の項がない、署名ファイルが空(または base64 でない)といった場合は、Draft を作らずに失敗する。壊れた更新マニフェストが配信されることはない。

## 誰が何をできるか

| 操作 | 書き込み権限者(共同開発者) | 管理者(メンテナー) |
|---|---|---|
| ブランチを作る、PR を出す | できる | できる |
| `main` にマージする | レビュー承認後にできる。ただし CODEOWNERS 対象のファイルは、コードオーナーの承認が必要 | できる |
| `v*` タグを作る | **できない** | できる |
| 署名鍵を使ったビルドを始める | **できない**(タグを作れず、承認もできない) | 承認すればできる |
| Environment や Ruleset の設定を変える | できない | できる |
| 署名鍵の値を読む | できない(GitHub は登録後に Secret を読み出せない) | できない(上書きと削除のみ) |

## 想定している脅威と対策

| 脅威 | 対策 |
|---|---|
| 共同開発者が、ワークフローを書き換えて鍵を盗む | 鍵は Environment に置き、`v*` タグ限定 + 承認必須。ワークフローの変更はコードオーナーの承認が必要 |
| 共同開発者が、タグを切って署名付きインストーラーを作らせる | タグの作成は管理者のみ(Ruleset)。さらに、鍵の使用に承認が要る |
| 配信元(GitHub 上のファイル)の差し替え | 署名を検証するため、秘密鍵がなければ適用されない |
| 公開鍵や配信先の差し替え(アプリ側) | `tauri.conf.json` と更新の確認処理はコードオーナーの承認が必要 |
| 壊れた版・誤った版の配信 | バージョンとCHANGELOGの整合チェック、Draft での人による確認 |
| 配布済みのタグの書き換え | タグの更新・削除を禁止(Ruleset) |
| デバッグ用の配信元の上書きが製品に残る | リリースのビルドで、その名前が実行ファイルに残っていないことを検査 |

## 残っているリスク

仕組みの限界として、次を把握している。

- **ビルド中のスクリプトは、署名鍵の環境変数を継承する。** ビルドの設定やスクリプト、依存パッケージのスクリプト(`beforeBuildCommand`、`build.rs`、npm のスクリプト)は、鍵のあるステップで動く。これらの変更は、CODEOWNERS の対象外のものがある(依存の定義など)。このため、**承認者は、承認の前に、タグが指すコミットまでの差分(依存・ビルド関連のファイルの変更を含む)を確認する**。根本的な対策は、ビルドを鍵なしで行い、署名だけを承認ジョブで行う構成への変更だが、まだ行っていない。
- **署名鍵にパスワードを付けていない。** 鍵のファイルを手に入れた人は、そのまま署名できる。鍵のバックアップは、リポジトリの外の、共有・同期されない場所に置く。パスワードを付けるには鍵の再生成が必要で、既存の利用者に影響する(下記)。
- **第三者の GitHub Action を、コミット SHA で固定していない。** 鍵は、ビルドのステップにだけ渡すので、影響は限られる。
- **管理者アカウントが侵害された場合は守れない。** Environment の承認者と、Ruleset の例外は管理者。`main` の保護は、管理者には強制していない。
- **Release の編集権限は、制限していない(未確認)。** 書き込み権限者が、公開済みの Release のファイルを差し替えられるかは確認していない。差し替えられても、有効な署名は作れないため、更新は適用されない。

## 運用上の注意

### 共同開発者を増やすとき

次を確認する。

```bash
# Environment: 承認者と、デプロイできる ref (tag v*)
gh api repos/<owner>/<repo>/environments/release
gh api repos/<owner>/<repo>/environments/release/deployment-branch-policies

# タグの Ruleset: 対象 (refs/tags/v*)、制限する操作、例外 (bypass)
gh api repos/<owner>/<repo>/rulesets
gh api repos/<owner>/<repo>/rulesets/<id>

# 署名鍵が Environment にだけあること(リポジトリ直下には無いこと)
gh secret list
gh secret list --env release
```

承認者を増やす場合は、承認者自身によるデプロイの承認(prevent self-review)を有効にするかを決める。単独のメンテナーの間は無効にしている。

### 署名鍵を失う、または差し替える場合

秘密鍵を失うと、既存の版に埋め込まれた公開鍵で検証できる署名を作れなくなる。**既存の利用者は、アプリ内で更新できなくなり、手動でインストールし直す必要がある。** 鍵を再生成する場合は、次の順に行う。

1. 新しい鍵ペアを作る(`npx tauri signer generate -w <出力先>`)。
2. 新しい秘密鍵を、Environment `release` の Secret として登録する。
3. 新しい公開鍵を `tauri.conf.json` の `pubkey` に反映する。
4. その版は手動のインストールが必要であることを、リリースノートに明記する。

秘密鍵は、リポジトリ、ログ、チャット、コミットのどこにも出さない。

### Actions が使えないとき

ワークフローを直せない、または急ぐ場合に限り、手元でビルドして手動で Release を作れる。手元の鍵を使うため、鍵の取り扱いに注意する。通常は使わない。
