`$1`（省略時はこの会話で直前に述べられた機能追加・不具合修正の依頼内容）を整理し、改善タスクのIssueとして起票する。`.claude/skills/github-workflow/SKILL.md` のIssueラベルの意味を踏まえること。

以下を順に行う。

1. **内容の整理**:
   - 依頼が「機能追加」か「不具合修正」かを判別し、タイトルを `[改善] <要約>` の形式で作る。
   - `.github/ISSUE_TEMPLATE/improvement.yml` の各項目を埋める:
     - **背景**: なぜこの改善が必要か
     - **スコープ**: 何を実施するか
     - **非スコープ**: 触らないこと（曖昧な依頼ほど明示する）
     - **要判断事項**: 実装方針で選択肢がある場合、推奨案と理由を添えて記載する（勝手に確定しない）
     - **DoD**: チェックリスト形式（`- [ ] ...`）で完了条件を定義する
     - **参照すべき設計書・関連資料**: 関係する `docs/` セクションや過去のPRがあれば挙げる
     - **ブランチ名**: `feature/<Issue番号>-<短い説明>` の型。Issue番号は起票後にしか確定しないため、この時点ではプレースホルダのまま提示する
   - 依頼内容が曖昧でスコープ・DoDを埋められない場合は、起票に進まず、ユーザーに直接確認する（不明点を残したまま起票しない）。

2. **カテゴリラベルの判定**:
   - `bug` / `ux` / `test-infra` / `perf` のうち最も近いものを1つ判定する（依頼の性質から機械的に判断できるため、ここでは確定してよい）。判断に迷う場合のみユーザーに確認する。

3. **確認**:
   - 起票前に、整理した内容（タイトル・本文全文・付与するカテゴリラベル）をそのままユーザーに提示し、Issueとして作成してよいか確認を得る。GitHub上への作成は他者から見える行為であり、無断で実行しない。

4. **起票**:
   - 承認後、`gh issue create --title "..." --label "<カテゴリ>" --body "$(cat <<'EOF' ... EOF)"` の形式で作成する。カテゴリラベルは付与するが、`ready`/`blocked`（着手可否）は付与しない。
   - 作成されたIssue番号・URLを報告し、「着手可否（ready/blocked）の判断は人間の確認待ち」であることを明記する。

**このコマンドは起票までで止まる。** 着手・実装には入らない（着手可否は人間の判断のため）。関連タスクの実装計画は `/issue-kickoff <Issue番号>` を使う。
