# GrayBrowser 依存パッケージ警告の整理ガイド

## 原則

- **重大度だけで判断しない。** `high` でも配布物に入らなければ利用者への影響はなく、`low` でも外部入力を処理する経路にあれば優先する。判断の軸は「配布物に入るか」「このアプリで到達するか」。
- **推測で分類しない。** 「開発用の依存だろう」「Linux向けだろう」といった推測で区分を確定させず、下記の確認コマンドを実行して出力を根拠にする。
- **調査と提案までを自動で行い、外部に作用する操作は承認後に行う。** dismiss・Issue起票・依存更新・設定変更は、提案を提示してユーザーの承認を得てから実行する。

## 手順

### 1. 警告の取得

```bash
gh api --paginate 'repos/{owner}/{repo}/dependabot/alerts?state=open&per_page=100' \
  --jq '.[] | [.number, .security_advisory.severity, .dependency.package.ecosystem, .dependency.package.name, .dependency.scope, .dependency.manifest_path, (.security_vulnerability.first_patched_version.identifier // "-"), .security_advisory.ghsa_id] | @tsv'
```

- `--paginate` を付け、100件を超える場合の取りこぼしを防ぐ。
- 同じパッケージの警告は複数件に分かれていることが多い(例: 1つのパッケージに別々のGHSA)。パッケージ単位にまとめて扱う。
- `scope` の `runtime` / `development` は、Dependabotがマニフェスト上の区分から付けたもので、**対象OSやビルドへの採用有無は考慮されない**。そのまま結論にしない。

### 2. Rust側は `cargo audit` と突き合わせる

```bash
cargo audit
```

- ワークスペースのルート(`Cargo.lock` がある場所)で実行する。CIの `audit.yml` が週次で実行している同じ検査。`--manifest-path` は受け付けない(エラーになる)。
- Dependabotに出ない "unmaintained"(メンテナンス終了)や "unsound"(健全性の問題)の警告は、こちらでしか分からない。両方の結果を並べる。これらは脆弱性そのものではなく、修正版が出ない場合が多いので、到達性(手順3)を確認した上で区分CまたはDにする。

### 3. 到達性を確認する(根拠を必ず残す)

**Rust**: Windows向けの配布物に入るかを、ターゲットを指定して確認する。

```bash
cargo tree --manifest-path src-tauri/Cargo.toml -i <クレート名> --target x86_64-pc-windows-msvc -e normal
```

- `warning: nothing to print.` と出れば、Windowsの配布物には入らない(GTK系などLinux向けの依存が典型)。比較のため `--target x86_64-unknown-linux-gnu` でも実行すると、誰が引いているかが分かる。
- `package ID specification ... did not match` というエラーは「入らない」ではなく、名前や版の指定が合っていない。区別すること。
- **警告に書かれた版と、`Cargo.lock` にある版は別物。** Dependabotの `first_patched_version` は修正版であり、現行版ではない。`-i` はクレート名で引き、複数版がある場合は `名前@版` で指定する。報告には現行版も併記する。
- npmと同様に、警告のあるクレートを一覧にして順に確認する(クレート名が多い場合):

  ```bash
  for c in <クレート名...>; do echo "## $c"; cargo tree --manifest-path src-tauri/Cargo.toml -i "$c" --target x86_64-pc-windows-msvc -e normal 2>&1 | head -5; done
  ```
- 出力があれば、どのクレートが引いているか(自分のコードが直接使っているか、tauri等の下流か)を記録する。`-e normal` は開発専用の依存(dev-dependencies)とビルド専用の依存(build-dependencies)を除く。ビルド時のスクリプトが問題になる警告では `-e build` も確認する。

**npm**: 依存元をたどり、配布物に入るかを確認する。

```bash
npm ls <パッケージ名>            # 依存元をたどる
npm ls <パッケージ名> --omit=dev  # 本番依存だけに絞る。空なら本番依存には入らない
```

- 警告のあるパッケージが多い場合は、パッケージ名の一覧を作って順に実行する(`for p in <名前...>; do echo "## $p"; npm ls "$p" --omit=dev 2>&1 | head -8; done`)。
- `--omit=dev` で何も出ない場合は、本番依存に含まれない。最上位の依存元が `package.json` の `dependencies` か `devDependencies` かも併せて見る。
- `dependencies` にあっても、ビルド済みの画面に実際に含まれるかは別問題。これも出力と `package.json` で確認し、「ビルドや開発サーバー用のツール」「E2Eテスト専用」といった分類は、確認した依存元に基づいて書く。
- 配布物に入らない依存でも、CIとリリースのビルドでは `npm ci` で導入される(`devDependencies` を含む)ため、ビルド環境には存在する。リリースのビルドは署名鍵を扱うジョブで動くので、報告には「配布物に入らない」と「ビルド環境には入る」の両方を書く。
- ビルド環境に入る依存の扱いの目安:
  - **区分Aの候補にする**: インストール時・ビルド時に任意のコードを実行できる種類の問題(悪意あるパッケージ、インストールスクリプト、ビルド中に処理される入力を介したコード実行)で、署名鍵のあるジョブの実行経路に乗るもの。
  - **区分B・Cにする**: 開発サーバーへのアクセスや、リポジトリ内の信頼できる入力を処理するときだけ成立する問題。リリースのビルドでは攻撃者が入力を差し込めないことを理由に書く。

### 4. このアプリの脅威モデルで重み付けする

優先度を**上げる**もの:
- 外部入力を処理する経路にある: 動画ファイルのメタデータ・ファイル名、FFmpeg/FFprobeの出力、更新マニフェスト(`latest.json`)、WebViewに表示する外部由来の文字列。
- 更新・署名・ファイル操作に関わる(`tauri` 本体、`tauri-plugin-updater`、ハッシュ・暗号関連)。
- WebViewに触れる。CSPが未設定(`null`)のため、画面側で任意のスクリプトが動くと Tauri の API(ファイル操作など)に届きうる。

優先度を**下げる**もの:
- 開発機・CIでの利用に限られる(開発サーバー、テストツール、lint、ビルドツール)。ただし、開発サーバー向けの警告でも、開発者がそのサーバーを起動して信頼できないページを開く場合に限った話であることを理由に添える。
- 攻撃にネットワーク越しの接続や、特定のOS・設定が必要で、このアプリの利用形態では成立しない。

### 5. 修正の可能性を確認する

- `first_patched_version` の有無を見る。**パッチが存在しない警告は更新では解決できない**ため、区分C・Dのいずれかになる(下の判定順を参照)。
- パッチがある場合は、ロックファイルの更新だけで済む(現在の依存範囲内)か、メジャーバージョンの更新が必要かを確認する。メジャー更新は破壊的変更を伴うので、別扱いにする。

## 分類と対応案

担当者によって結論が変わらないよう、次の順に判定する。

1. **配布物に入るか**(手順3の出力で判定)
   - 入り、かつ手順4の「上げるもの」(外部入力の処理、更新・署名・ファイル操作、WebView)のいずれかに該当する → **A**。
   - 入るが、上のいずれにも該当しない → 修正版が依存範囲内にあれば **B**、なければ **D**。
2. **入らない場合**
   - 修正版が依存範囲内にある → **B**(更新のコストが低く、dismissの説明責任も残らないため、原則として更新を選ぶ)。
   - 修正版がない、またはメジャー更新が必要で見合わない → **C**。
3. **判断できない場合**(到達性を確認できない、影響の範囲が不明など) → **D**。

| 区分 | 条件 | 対応案 |
|---|---|---|
| A 要対応 | 上の1で「入り、かつ該当する」 | Issue化(`/issue-file`)→ Plan承認 → `implementer` で更新 → `reviewer` で検収 |
| B まとめて更新 | 修正版が依存範囲内にある(配布物に入るかは問わない。入らないものはまとめて更新する) | 依存の更新を1つのPRにまとめる(ロックファイルのみ) |
| C dismiss候補 | 配布物に入らず、修正版がない(またはメジャー更新が必要で見合わない) | 理由と根拠コマンドの出力を添えてdismissを提案する |
| D 様子見 | 判断材料が不足している | 何が分かれば判断できるか(確認するコマンドや情報)と、再確認の契機(次回のリリース前の整理、上流の更新など)を書く |

`cargo audit` の "unmaintained" / "unsound" の指摘は、次のように扱う。

- Windowsの配布物に入らない(手順3で `nothing to print`) → **C**(`not_used`)。
- 入る → 修正版がなく上流(`tauri` など)の更新待ちになることが多いので **D**(契機: `tauri` 関連の更新時)。ただし、"unsound" で外部入力が通る経路にある場合は **A** を検討する。

dismissの理由は、GitHub REST APIの `dismissed_reason` の値(`fix_started` / `inaccurate` / `no_bandwidth` / `not_used` / `tolerable_risk`)のうち、次の対応で使い分ける。

| 理由 | 使う場面 |
|---|---|
| `not_used` | 配布物に入らない、対象OS(Windows)に入らない、使っていない機能 |
| `tolerable_risk` | 配布物またはビルド環境に入るが、評価した上で許容する(評価の根拠をコメントに書く) |
| `inaccurate` | 警告そのものが誤っている |

`fix_started` / `no_bandwidth` は使わない(対応を先送りする理由にしない。先送りは区分Dとして扱う)。

## 実行ゲート

調査では、`gh api` を読み取り(GET)にしか使わない。`-X` / `--method` を付けた呼び出しは書き込みなので、承認なしに実行しない。

次の操作は、提案を提示し、ユーザーの承認を得てから実行する。承認は、警告番号を明示した対象に対してのみ有効とする(「区分Cを全部」のような包括的な承認は、対象の番号を確認し直してから実行する)。

- 警告のdismiss(`gh api -X PATCH repos/{owner}/{repo}/dependabot/alerts/<番号>`): 理由と理由のコメントを必須にする。1件ずつ、承認された番号だけを実行する。
- Issueの起票: `/issue-file` の手順に従う。
- 依存の更新: `github-workflow` スキルに従い、featureブランチを作成してPRを出す。実装に影響する変更のため、CLAUDE.md のPlan承認ゲートを通す。ロックファイルだけの更新でも、更新後に `cargo test --all-features --workspace` や `npm run lint` / `npm run typecheck` などの検証を行う。
- Dependabotの有効化・設定ファイルの追加などの設定変更。

## 報告形式

区分ごとに表で報告し、各行に根拠を添える。

```
### 要約
(3行以内。件数と、対応が必要なものの有無)

### A 要対応 / B まとめて更新 / C dismiss候補 / D 様子見
| 警告 | パッケージ | scope | 到達性の根拠 | 推奨対応 |
```

- 「到達性の根拠」には、実行したコマンドと出力の要点を書く(例: `cargo tree -i <クレート> --target x86_64-pc-windows-msvc` が空)。
- 同じパッケージの複数の警告は1行にまとめ、警告番号を列挙する。
- 取得できなかった情報や、確認できなかった点は、そのまま明記する。

## 見直すタイミング

- リリースの前(`release-publish` スキルの手順に入る前)。
- CIの `cargo audit` が失敗したとき。
- 依存パッケージを更新したとき。
