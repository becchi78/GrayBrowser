# GrayBrowser バージョン更新ガイド

## 対象

アプリ本体(Rust/フロントエンド)のコード変更を伴うPRのみが対象。ドキュメント・CI設定・`.claude/`配下の運用ファイルのみの変更(スキル追記、CHANGELOG運用整備、`.gitattributes`調整等)はバージョンを上げない。

例外として、まとめリリース(下記「リリース単位」)の**リリース用PR**(バージョン更新・CHANGELOG・READMEのみを含むPR)は、コード変更を伴わなくてもバージョンを上げる。`release-publish`で未更新のバージョンをPR経由で更新する場合も、同じくこの例外に当たる。

## リリース単位

- **個別リリース(既定)**: PRごとに下記の分類基準で判定してバージョンを上げる。パッチ(バグ修正・軽微な調整)は原則こちら。**コードの変更、バージョンの更新、`CHANGELOG.md`の項、`README.md`の更新(バージョン表示と、必要なら機能の追記)を、1つのPRに含める**(CHANGELOG/README用の別PRは作らない)。順序は「そのPRをマージ → タグpush → Actionsが Draft を作成 → 確認して公開」で、タグはそのPRがマージされた`main`で`release-publish`の手順に従って打つ。
- **まとめリリース**: ユーザーが「まとめて vX.Y.0 にする」のように明示的に指示した時点で開始する。対象の機能PRではバージョン・CHANGELOGを上げず、終了はユーザーの指示で**リリース用PR**(3ファイルのバージョン更新 + `CHANGELOG.md` + `README.md`)を出す時点とし、そのマージ後にリリースする。機能が出揃ったらClaudeが提案してよいが、勝手にリリース用PRを出さない。指示がなければ個別リリースとし、Claudeの判断でまとめない。

まとめリリースのバージョン番号は、リリース用PR時点の`main`のバージョンから、含まれる変更のうち最も大きい分類で1つ上げる。リリース用PR作成時は、前回タグ以降にマージ済みのPRを`gh pr list --state merged`等で列挙し、まとめ対象を確認する。

### まとめリリース中に急ぎのパッチが必要になった場合

`main`にはまとめ対象のPRが既にマージ済みのため、パッチ単体のリリースはできない。Claudeが勝手に決めず、ユーザーに確認する。選択肢は次のとおり。

- まとめ分を含めた版として前倒しリリースする(バージョンは含まれる変更の最大分類で決める)。
- まとめ対象の追加マージを止め、先にまとめ分をリリースしてから修正する。

## 分類基準

- **パッチ**(例: `0.1.0` → `0.1.1`): バグ修正、軽微な修正・調整。
- **マイナー**(例: `0.1.0` → `0.2.0`): 重要と判断した新機能追加、ユーザーが体感する動作変更。
- **メジャー**: Claudeは判断・実行しない。破壊的変更やメジャーアップに相当すると感じた場合は、必ず`AskUserQuestion`でユーザーに確認する。ユーザーからの明示的な指示がない限り上げない。

パッチかマイナーか迷う場合は、小さく見積もる(パッチ側に倒す)。

## 更新対象ファイル(3箇所を同期させる)

- `package.json` の `version`
- `src-tauri/tauri.conf.json` の `version`
- `src-tauri/Cargo.toml` の `[package] version`

あわせて、次も同じPR(個別リリース)またはリリース用PR(まとめリリース)で更新する。`scripts/release/check-version.mjs`が検査するのは上の3ファイルと`CHANGELOG.md`の項だけなので、この2つは検査されない(更新を忘れてもタグ前に検知されない)。

- `Cargo.lock` の `graybrowser` のエントリ(`Cargo.toml`の更新に追従する)。
- `README.md` のバージョン表示(バッジの`alpha (x.y.z)`と、「現在のバージョンは **x.y.z(開発版)** です」の文)。

## 手順

1. PRに含める変更内容(まとめリリースのリリース用PRでは、含まれる全変更)を上記の分類基準で判定する。メジャー相当と感じた場合はここでユーザーに確認する。
2. 3ファイルから現在のバージョンを確認する(通常は同期しているはず。ズレていた場合はユーザーに報告してから進める)。
3. 判定結果に応じてSemVerを1つ上げ、3ファイルすべてを同じ新バージョンに更新する。
4. そのPRのコミットに含める。個別リリースでは、同じPRに`CHANGELOG.md`の項と`README.md`の更新も含める(`release-publish`の手順2・3)。まとめリリースの各PRでは、バージョンもCHANGELOGも更新しない。

## release-publishスキルとの関係

バージョンを上げたら、間を置かず(下記の各リリース単位のタイミングで) `release-publish` スキルの手順に従って実際にリリースする(`CHANGELOG.md`への記載・タグpush・ActionsがDraftとして作ったGitHub Releaseの確認と公開まで)。バージョン番号を上げるだけでリリースを後回しにしない。

- 個別リリース: コード・バージョン・CHANGELOG・READMEを含むPRのマージ後、間を置かずリリースする。
- まとめリリース: リリース用PRのマージ直後。それ以前の機能PRのマージ時点ではリリースしない。
